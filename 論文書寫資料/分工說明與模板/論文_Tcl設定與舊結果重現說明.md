> **歷史流程紀錄。** 供追溯舊結果；固定 10 ns 論文路線的數據與方法見 [工作站操作與資料說明](./工作站操作與資料說明.md)。

## 目前採用的原則

以老師提供的 `test/02_SYN/syn.tcl` 與專案原本的 Tcl 為依據，不為了讓結果變漂亮而調參數。「學校範本的設定」和「軟體未指定時的預設值」不同：例如 0.5 ns 是範本明確寫入的假設，不是所有論文共同的標準。公平比較需要四版使用一致且公開的條件。

四版已恢復輸入轉換時間 0.5 ns，移除 core 的 load_state 提早至 0.1T 抵達的設定，也移除新增的切換頻率指定。功耗由 DC 在未匯入實際波形、未手動指定切換頻率的條件下估計，與舊流程採用相同原則；不能稱為量測功耗。

## Tcl 在做什麼

Tcl 是交代合成工具工作的文字指令。合成就是把 Verilog 電路描述轉成製程提供的邏輯閘。它不只「把程式翻譯」，也會按你給的時間與負載條件選用不同大小的閘，因此設定會影響面積與功耗。

| 指令／名詞 | 沿用設定 | 白話定義與例子 |
|---|---|---|
| analyze、elaborate、link | 依該版本檔案與頂層 | 讀程式、建立電路、連上所需元件。頂層是整個電路的入口，例如完整 SHA3 的 top。 |
| target_library | 原 Makefile 的 TSMC40 TT、0.90 V、25°C | 元件資料庫，提供閘的大小、速度與功耗。換資料庫就像換不同規格的零件，不能當作相同實驗。TT 是典型製程條件。 |
| create_clock | 掃描週期 T | 每隔多久來一次時脈。例如 10 ns 對應 100 MHz。 |
| input/output delay | 最大 0.5T、最小 0 | 預留給電路外面的時間。10 ns 時，假設輸入最晚 5 ns 才到，輸出也要留 5 ns 給後方電路。不是電路內部實際延遲。 |
| input transition | 0.5 ns | 輸入從低電位升到高電位等轉換所花時間；不是訊號隔多久切換一次。 |
| clock transition | 0.1 ns | 同上，但描述時脈邊緣。 |
| clock uncertainty | 0.1 ns | 預留時脈不確定的裕量，工具可用的時間會因此減少。 |
| set_load | 0.05，依 library 單位 | 輸出要推動的電容負載，可理解為後面接的電路有多重；單位需看報告。 |
| max_transition / capacitance / fanout | 3 / 0.15 / 10，沿用範本 | 限制訊號轉換速度、電容、連接端點數。例如 fanout 10 是一個來源最多連接十個負載端點的限制。製程庫可能另外有更嚴的限制。 |
| set_fix_hold | 沿用原本要求 | 請工具修正資料過早抵達造成的問題；不代表所有違反一定能修完。 |
| wire_load_mode top | 沿用 | 在還沒有實際佈線時，以頂層設計方式套用線路負載模型；不是實際晶片佈線結果。 |
| compile_ultra | 沿用 | 執行電路最佳化與元件映射；映射就是挑選資料庫中的實際邏輯閘。 |
| report_* / write_* | 報告及輸出 | 保存面積、功耗、時間分析及閘級電路等資料。增加報告本身通常不改變電路，改最佳化指令或約束則可能改變。 |

## 為什麼現在會看到失敗

Slack 是「允許抵達時間－實際抵達時間」。例如允許 5 ns、卻在 6.5 ns 抵達，slack 就是 −1.5 ns。這表示該時間要求沒達成，不等於 RTL 功能測試失敗。

CONSTRAINT_FAIL 表示其他限制違反。例如原輸入 transition 0.5 ns 比報告中的 0.38 ns 製程限制更慢。這次保留原設定並誠實標示違反，不把 0.5 改成 0.1 來消除標記。以前的 sweep 主要看 slack，未同樣檢查所有這些限制，因此以前沒顯示不代表以前不存在。

獨立 core 新增了外部 load_state 入口，通往下降緣的控制暫存器。10 ns 時下降緣在 5 ns，若輸入也允許 5 ns 才到，內部幾乎沒有剩餘時間可用。這是新 core 邊界與原範本假設的衝突，不能直接解讀成 Keccak 計算本身只能跑那麼慢。目前不修改此假設，也不把這種結果當成核心極限頻率；若要調整，需另外說明並確認。

## 舊 C3 的獨立重現

位置：`四版本程式/legacy_C3_reproduction/`。這是歷史對照組，不是第五種新架構。原始碼、Makefile、syn.tcl 直接由 Git commit `93cdc28337f97c38a1170f958b1065d55cf4bccb` 匯出，原樣保留，另附 SHA-256 清單（每個檔案內容的識別碼）。目標為 `others/sweep_summary_C3.csv` 的 10 ns 列。

四版 paper Tcl 仍有新增的保護電路保留、重設／注錯路徑處理、獨立 core 與額外報告，因此不能宣稱它和舊 Tcl 完全相同。此歷史對照組刻意直接執行原 Tcl，不經 paper Tcl。

上傳整個 `legacy_C3_reproduction` 到工作站 `~/sha3_paper_build/`。不必再 build，也不覆蓋四版已通過的 00/01。逐行執行：

```text
cd ~/sha3_paper_build/legacy_C3_reproduction
bash run_legacy_10ns.sh
```

只跑一次 10 ns 完整 SHA3 合成。使用原 Makefile 的 `make syn PROCESS=TSMC40`，產物保存在 `results/日期時間_PID/`，包含實際用到的 RTL、Tcl、Makefile、產生的 `.synopsys_dc.setup`、console.log、syn.log、Report、Netlist、DDC 及 historical_comparison.csv。Python 2.7 可讀取結果；Python 不負責合成或改變最佳化。

結果 `[MATCH]` 代表在舊 CSV 記錄的小數精度下，所有對照欄位一致。`[DIFFERENT]` 代表合成報告可讀但數字有差，CSV 會列出差值；不要為了匹配數值改參數。`[FAIL]` 表示執行或報告有錯，需要先查 log。MATCH 不等於通過新的所有約束檢查，因為原 Tcl 沒有輸出完整違反清單。

| 10 ns 舊紀錄 | 預期值 |
|---|---:|
| 面積（library 單位） | 43698.68854 |
| 動態功耗 mW | 1.6115 |
| 漏電功耗 mW | 0.2768897 |
| 完整 SHA3 總功耗 mW | 1.8883897 |
| core 理論吞吐量 Gbit/s | 0.453333333 |
| 完整功耗／core 理論吞吐量 pJ/bit | 4.16556552 |
| slack ns | 1.46 |

正確公式不是「功耗除以 240」。240 是一次 permutation（Keccak 狀態轉換）的舊理論週期數：吞吐量 = 1088 / (240 × T) Gbit/s；估計能量指標 = 完整 SHA3 功耗 mW / 此吞吐量。10 ns 時吞吐量約 0.453333333 Gbit/s。此歷史口徑和實測完整訊息吞吐量分開列，不能當作完整訊息的實測能耗。比較器亦保留舊腳本的九位有效數字中間捨入方式。

工具版本、資料庫版本、原始碼、設定都可能影響是否精確重現；舊 CSV 無法單獨證明當時所有環境。因此先跑此單點，對照後再決定四版正式掃頻。四版 00/01 本次未變動；新合成設定與歷史重現尚未在工作站執行，不宣稱已通過。
