# 四版合成重跑：以已重現的 C3 為基準（2026-10-28）

> **歷史重跑指南。** 固定 10 ns 論文路線使用已回收的四版結果；若須重跑，依 [工作站操作與資料說明](./工作站操作與資料說明.md)。

## 已確認與尚未確認

使用者回傳原 C3 10 ns 結果：動態功耗 1.6115 mW、漏電 0.2768897 mW、總功耗 1.8883897 mW、slack 1.46 ns，均與歷史紀錄相同。面積 43698.688536 四捨五入至歷史五位小數為 43698.68854。240-cycle 口徑能量為 4.16556552 pJ/bit。這證明這個歷史單點可重現，不代表四種架構已合成完成。

四版新版掃頻仍需在工作站執行。本次沒有改四版 00_TESTBED / 01_RTL，不必重新跑已通過的 RTL；仍會檢查工作站 rtl_latest.json 的來源檔案識別碼，不會用口頭通過取代它。

## 合成基準與必要差異

1. 仍用原 Makefile 產生 TSMC40 設定；DC 啟動參數補齊為原 Makefile 的 `-x "set_host_options -max_cores 4" -output_log_file syn.log`。這是每個合成程序可使用的 CPU 核心數，不是電路的 Keccak core。四版平行最多是四個合成程序，每個最多使用四顆 CPU 核心。
2. 保留原 0.5 ns 輸入轉換時間、0.1 ns 時脈轉換時間與裕量、半週期輸入／輸出延遲、0.05 輸出負載及原限制。不指定新的訊號切換頻率。
3. V0 full 使用 `paper_c3_reference.tcl`：原 C3 Tcl 的合成與原輸出指令完整保留，只把最後 exit 換成額外報告與輸出。沒有加入新的最佳化指令。V0 full 10 ns 自動比較歷史面積、動態／漏電功耗、slack；不一致就停止 V0，避免繼續累積不可比資料。
4. V0 已通過 RTL 的 sha3_pkg 中，兩個常數表宣告曾為舊工具相容性改成 packed localparam，常數內容相同；其餘原始 RTL 文字相同（換行不同）。這次不動它，因此仍需由新掃頻的 C3_REFERENCE_MATCH 確認結果，不能只靠先前獨立歷史資料夾的通過推定。
5. V1／V2／V3 保留先前保護電路的預先合成、保留階層及注錯入口處理。這些是為了不讓最佳化把錯誤檢查硬體刪掉；不能直接套用無保護 C3 的全部指令。沒有因本次重跑而放寬限制。報告檢查保護單元數量與面積，不代表已完成閘級故障驗證。
6. 獨立 core 仍保留原半週期輸入假設，不自行改成較早抵達。負 slack 若來自 load_state 的半週期路徑，反映這個外部介面條件，不能說是 Keccak 計算本身的極限。

名詞的白話定義與例子請見 TCL_BASELINE_GUIDE.md。

## 更新到現有工作站資料夾

先確認沒有舊掃頻正在執行。將最新的 `sha3_paper_complete.zip` 上傳至 `~/sha3_paper_build/`。以下指令只更新四版 02_SYN、準備檔清單與啟動／說明檔，不覆蓋 00/01、rtl_latest.json、.synopsys_dc.setup 或歷次 results。ZIP 不含工作站 .synopsys_dc.setup。

```text
cd ~/sha3_paper_build
unzip -o sha3_paper_complete.zip 'V*/02_SYN/*' 'V*/prepared_hashes.csv' run_dense_sweep.sh run_four_sweeps.sh RERUN_GUIDE.md TCL_BASELINE_GUIDE.md
```

若沒有既有四版資料夾，完整解壓後需要先跑四版 RTL；這不是現有工作站的情況。

## 先確認四版各一個週期

```text
cd ~/sha3_paper_build
bash run_four_sweeps.sh check
```

四版平行，每版先 full 10 ns 再 core 10 ns，共八次合成。啟動器結束後，查看 log：

```text
set logdir = `cat latest_sweep_logs.txt`
tail -n 25 "$logdir"/*.log
```

應確認 V0 出現 `[C3_REFERENCE_MATCH]`，四版沒有 `[TOOL_ERROR]`／`[EXECUTION_ERROR]`。`CONSTRAINT_FAIL` 或 `TIMING_FAIL` 仍可能存在，是保存的分析結果；不等於程式執行中斷。若沒有完整有效點，會明示 `COMPLETED_NO_VALID_DATA`，不是全約束通過。

## 正式背景掃頻：10.0、9.9、…、1.0 ns

前一項沒有工具／報告／基準錯誤後執行：

```text
cd ~/sha3_paper_build
nohup bash run_four_sweeps.sh dense < /dev/null >& dense_launcher.log &
```

這個指令適用你的 tcsh。只有一條背景啟動指令；腳本內部平行啟動四版。每版 91 個週期 × full/core = 182 次，四版共 728 次。每個版本內依序跑，保留所有成功及失敗點。沒有刪舊紀錄，也不把負 slack 當工具錯誤中止。

```text
cat dense_launcher.log
set logdir = `cat latest_sweep_logs.txt`
tail -n 15 "$logdir"/*.log
```

啟動器有防重複鎖，請不要同時用舊的四條單獨 nohup 指令；那些不受這個鎖控制。四版各自 log 與 PID 會在啟動時列出。執行中每點會報進度、slack 與限制違反摘要。不要只憑 `[STARTED]` 判定整批成功。

## 資料與判讀

每版結果保存在 `V*/results/sweep/日期時間/`：

- `sweep.csv`：各個週期的面積、功耗、slack、限制及各種計算口徑。
- `request.json`、`synopsys_dc.setup`、`rtl_summary.json`：當次設定與 RTL 來源。
- 每個 full/core 點下的 `02_SYN`：Tcl、dc.log、syn.log、Report、Netlist 等原始產物，並保留用到的 00/01。
- `sweep_summary.json`：`status=COMPLETED` 只代表所有要求的點執行完成；`strict_validity` 才表示是否各 scope 至少有符合所有檢查的點。工具／報告錯誤為 ERROR。
- `operating_points.json`：各 scope 最短達標取樣週期、最低估計能量、負 slack 點及相鄰取樣點的正負變化。若沒有合格點，欄位是 null，不捏造最佳操作點。

| CSV 欄位 | 意義 |
|---|---|
| timing_met | slack ≥ 0，只代表時間要求達標。 |
| all_constraints_met | 時間與目前檢查的其他限制都達標。 |
| legacy240_throughput_gbps | full 的舊理論吞吐量 1088/(240×週期)。只在時間達標時計算。 |
| legacy240_full_power_normalized_pj | 整顆功耗除以上述吞吐量，保留舊腳本的九位有效數字捨入。 |
| legacy240_qualification | 明示其他限制是否違反；不能當成全約束通過數據。 |
| full_throughput_gbps / estimated_energy_per_bit_pj | 全部限制達標時，使用完整 4096-byte 測試的週期數計算。 |
| core_rate_throughput_gbps | 使用 TB 實際 core 週期（先前為 241），不是歷史假設 240；要全部限制達標才列。 |

`operating_points.json` 同時列「僅時間達標的舊口徑」及「全部約束達標」兩類最佳值，兩者不可混稱。若 core 全程負 slack，沒有核心極限頻率結論；若 1 ns 仍達標，掃描範圍內沒有找到失敗邊界。合成結果也可能不單調，腳本會列出所有相鄰正負變化，不能只假設一個邊界。

完成後執行 `bash collect_results.sh` 收集四版結果。原 C3 重現資料夾的結果另行保留，作為歷史重現的佐證。
