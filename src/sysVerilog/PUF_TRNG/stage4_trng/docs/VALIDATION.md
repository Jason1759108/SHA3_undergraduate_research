# 發布前驗證與界線

這個階段不拿舊 PASS 當新接線的驗證。SHA3 與健康來源 RTL 各自凍結，新工程重新打包、產生接線圖、跑完整系統模擬與實體實作，最後才發布配對八檔。

## 已設計的發布門檻

| 檢查 | 主要涵蓋內容 |
|---|---|
| 凍結來源及 IP 複本 | 19 份 RTL 與來源階段、打包後實際使用的來源逐一核對 |
| SHA3 normal | 原本研究 testbed 的正常案例 |
| SHA3 ft | 153 個 parity/replay 故障注入與修復案例；是模擬注入，不宣稱已實板注入 |
| SHA3 AXI | 兩輪已知向量、輸入／輸出等待、錯誤 header、提早 TLAST、錯誤 TKEEP、中途重設後恢復 |
| 健康來源 unit | 合法／錯誤存取、AW/W 分開到達、回覆等待、啟動與保留階段健康失敗、最後樣本失敗優先、中止、看門狗與復原；部分門檻縮小以快速驗證控制邏輯 |
| 實際整合 BD | 36 次已知 SHA3 比對，另有兩次 1024-byte 來源 RAM 實際讀回後送進 DMA/SHA3 的摘要比對；啟動 RCT、APT、保留階段 RCT、最後樣本失敗、中止、RAM 拒讀、重設與恢復 |
| PYNQ host | 原版 PYNQ 2.5 解析器及 DMA 傳輸程式，搭配模擬 MMIO／配置／下載；單一 overlay、反覆產生、健康失敗禁止讀 RAM／啟動 DMA、錯誤摘要／狀態／長度、傳輸錯誤／逾時、記憶體所有權、停止失敗不重新設定 FPGA |
| 操作本與收集器 | 完整執行本階段自己撰寫的 Notebook（模擬硬體），包括 16 批與 1000 批；檢查 1,024,000-byte raw、32,000-byte 摘要、1,000,000-byte 重啟矩陣；失敗也保留 ZIP，不補抽來掩蓋失敗 |
| 實體實作 | 完成 write_bitstream；WNS/WHS 不可負；沒有 Error/Critical Warning 等級 DRC；8 個 NAND LUT2、88 個反相 LUT1，逐環長度及 16 個 ASYNC_REG 同步器均須正確 |
| 配對發布 | 系統模擬及原版解析器使用的 HWH 指紋，須等於發布 HWH；測試來源指紋不得過期；ZIP 解壓內容再核對一次 |

WNS 是最差設定時間餘裕，WHS 是最差保持時間餘裕；負值表示不能通過這裡的發布門檻。DRC 是工具的設計規則檢查。CDC 是跨時脈檢查；RO 本來就是非同步來源，即使 CDC 報告沒有項目，也不能當作熵或亞穩態安全性的證明。

實際門檻結果及數字見 `build/final_validation.json`、各 `*_pass.json`、`system_sim_result.json` 及 `build/reports/trng_integrated/`。發布包內 manifest 也保留各測試的來源指紋。

## 系統模擬到底看到了哪裡

PS 的驗證模型從模型 DDR 提供輸入；接收摘要使用**獨立觀察器**核對 PS HP0 邊界真正接受的寫入位址、五個 64-bit 資料拍、最後一拍 byte strobe、B 回覆、完整 36 bytes 及緩衝區界線。

這不是在 Linux 上實際讀回 DDR。先前驗證發現此版本 VIP 的 DDR 後門資料未反映被接受的 HP0 寫入，所以刻意不把後門讀值當證據；真正 DDR、CPU 快取及 Linux 記憶體配置的最後確認仍由上板 Notebook 做。

模擬使用可控制的數位取樣來驗證健康檢查／資料路徑，不能模擬出真實 RO 的隨機抖動。實體查核則確認 `.bit` 的 RO 確實存在；兩者用途不同。

## 軟體保護

來源成功狀態必須精確符合 status=194、count=1024、observed=2048、startup_seen=1024、各故障遮罩=0、RO 關閉；讀 RAM 前後、完成 SHA3 後都重新確認狀態。

DMA 是「可直接碰主記憶體的硬體」。因此傳輸錯誤後保留配置的記憶體；復原要先確認兩通道 Halted，再釋放，最後才重新設定 FPGA。停止失敗則保留記憶體並停止流程。PYNQ 2.5 的無限 `wait()` 迴圈在本階段改成有逾時與錯誤檢查的輪詢，成功後才同步接收快取。

這些軟體逾時都假設底層 MMIO 還能回應。如果處理器或 AXI 存取本身陷入無法返回的系統問題，Python 沒有辦法保證中斷或自救。測試通過可排除已涵蓋的接線／控制錯誤，不能保證網路、電源、SD 卡、Linux 或其他使用者永遠不出問題。

## 尚不能聲稱

- 本階段尚待使用者實板驗收；離線模擬的 PASS 不是實板 PASS。
- 新布局的原始熵估計與重啟分析需使用本次收集檔，舊 6.638383 bits/樣本不直接繼承。
- 1000 次 RO 啟停不是 1000 次整張板子斷電重啟；若用途要求開機、溫壓變化或跨板評估，需另設實驗。
- 多路訊號可能相關，不能把八路單獨估計相加，也不能把每個樣本的估計直接乘上批次長度當保證。
- 目前 SHA3 對 raw 做固定壓縮，尚未建立正式熵信用與允許輸出量的安全論證。
- 摘要與 Python 相符，只證明計算功能；看起來均勻的摘要不證明原始來源不可預測。
- 低功耗、產出速率、溫度／電壓穩健性與正式密碼學用途的資格仍未驗收。

## 重建

組員如需重建，可執行 `python sim/build_release.py`。需 Windows、本機 Vivado 2025.2（預設 `D:/VIVADO/2025.2/Vivado/bin`）與 Python；也會使用本專案保留的 stage1 板卡定義與原版 PYNQ 2.5 相容性來源。更換 Vivado 路徑時加 `--vivado-bin`。整個程序只在本機建置／模擬，不連板子、不上傳、不推 Git。

完整 Vivado 工作工程與快取放在被 Git 忽略的 build 子目錄；發布八檔、精選測試證據與報告會保留。修改 RTL、IP、接線或 Python 後，必須重新通過對應門檻並重新發布，不可手改 manifest 來跳過核對。
